**第7节逐问回答**

1. **CPU 风险被低估。** 20–80 ms 无测量依据，单次低于100 ms也不是整请求门槛；一次回答允许8次工具调用（W/search-chat.ts:18），还包含解析、排序、校验。档位数字正确，但应检查 **Workers计划**，结合本地 CPU profile、部署后 invocation CPU p95/p99及超限率验收，不能只看配置与单次墙钟。[官方限制与测量](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)

2. **先不排队可接受，但超时不等于未写入。** 服务端可能提交后丢响应；重新生成 UUID 会重复。先保留原操作 ID并回读确认。若确需队列，最小方案是账号绑定的待提交操作、固定 ID、原 base、409停住、待提交不注入记忆；还须补幂等确认。待提交日志不是第二份已提交真相源（W/recall.ts:113–123）。

3. **能直接判定规则：同服务、同 issuer/sub 的 cloud 会话使用同一 recall 账号。** `remote-auth.ts:31` 生成 owner；`:64` 只接受 cloud，phone/host会话返回认证失败，并非另一账号；`cloud.ts:70` 返回 owner，`index.ts:117`传给存储。iPhone云登录也是 cloud（I/RemoteService.swift:223）。禁止改成 email 哈希。实际两设备是否登录同一身份需运行态核实；个人 token 模式则固定 `personal-client`。

4. **审批档位合适。** 跨设备持久写入不应比本地全局记忆更宽松。现有全局写入也明确排除自动放行（R/tools.rs:337–350）。审批应展示全文、删除对象和云账号，不能只复用理由字符串。

5. **中文判断部分准确。** unicode61不做中文词切分，但“整段一个token”忽略标点；trigram的短词限制针对 MATCH，LIKE仍可退化扫描。D1支持FTS5，RFC自己的短词LIKE兜底已是低成本办法。草案外部内容索引还缺维护机制，不能只双写普通表。[SQLite](https://www.sqlite.org/fts5.html)、[D1](https://developers.cloudflare.com/d1/sql-api/sql-statements/)

6. **反对通用 MCP“启用即自动执行”。** 工具名白名单不限制参数、收件人或删除范围，不能等同具体授权。更便宜的首版只接经核验的只读工具，写工具暂不开放；避免为可选能力先建云审批流。

7. **先补验收事实。** 工作包1/2已有本地验证，但未证明生产链路；先做已授权范围内的端到端验证，再测检索覆盖率。无需先抽注册表或纯内核。
