2026-09-12。用户关注500、1000字输入时的逐行增高。下文保留初次审查的实测事实；后续已按[Grok参考输入面板](compact-composer/README.md)实施逐行增高、展开编辑和转写跟随。最终验收见原生design-qa末尾，原审查截图不代表当前版本。

## 发现

1. **P1：长草稿中的语音新增内容不可见。** 步骤4的转写数据含新增句，但视图仍停在开头；用户无法及时核对识别。`VoiceComposerPanel`使用固定高度ScrollView，没有滚到新文字的机制。应让录音默认跟随新增片段；用户主动向上阅读后暂停跟随，提供“回到最新”入口。
2. **P2：键盘输入的高度上限偏保守，缺少展开入口。** 步骤2/3都仅101.33pt。当前`ComposerTextInput`的上限是`min(170, lineHeight * 5)`，不是完全不增高，但长文很早就进入窄小滚动区。应按可用空间确定上限，并在溢出时提供较大编辑区域。
3. **P2：语音区只按字号定高，不按行数增长。** 步骤4仍保留固定约104pt正文区，关闭键盘后有空间却未利用。短句和长句应共用“内容自然高度→上限→内部滚动”的规则。
4. **已有优点应保留。** 本轮500/1000字符没有截断；UITextView能显示键盘当前插入点；发送按钮始终可达，取消口述不损失原文。优化不能破坏这些行为。

## 建议交互规格

基本规则：宽度保持稳定，按实际排版后的行数逐步增高；达到上限后滚动。字符数不直接决定高度，因为中文、英文、换行、字体与屏宽会改变排版。

| 情形 | 建议行为 |
| --- | --- |
| 短句 | 一行起步，每新增一行自然增高；删除内容后同步收回高度 |
| 常规长输入 | iPhone17普通字号初始目标约6–8行，再按键盘以上可用空间、导航、操作栏与附件占用调整；SE和大字模式不能硬套同样行数 |
| 达到上限 | 内容区内部滚动，操作区固定；顶部仍保留部分对话空间，不无限长到遮住整个会话 |
| 500–1000字核对 | 出现“展开输入”入口，打开原生大面积编辑器；可滚动查看全文，仍是同一份草稿。收起保留光标、文本与附件，不增加“确认放入输入框”步骤 |
| 键盘编辑 | 新输入、换行或粘贴后保持当前光标可见；回到前文修改时不要强制跳到全文末尾。中文拼音组合态不重写UITextView.text |
| 持续口述 | 文本区随排版增高；达到上限后默认跟随识别中的新增片段，而非只显示原草稿。用户手动回看时暂停自动跟随，点击“回到最新”恢复 |
| 语音转编辑 | 收齐final后带着当前插入位置进入编辑；已有长文可继续展开，旧识别回调不能覆盖手改内容 |
| 大字和小屏 | 优先保证一个完整可读行、所有主要操作以及内部滚动；展开编辑作为长文阅读的补充，不把正文缩小来塞满一屏 |

500–1000字仍作为普通文本编辑，不因长度自动截断或强制变成附件。另一个边界是当前ASR单次60秒录音上限；这不等于文本只能保存60秒对应的字数，也不能用本轮脚本模拟证明能真实口述1000字。

## 竞品资料与证据边界

- [ChatGPT官方更新记录](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)可确认超10,000字符粘贴会转附件，用户可切回文本；这是超长粘贴策略，不能用于推断500/1000字的编辑器高度。
- [Claude Mobile听写说明](https://support.claude.com/en/articles/10065434-use-dictation-on-claude-mobile)确认麦克风、口述、箭头发送和X取消，没有给出逐行增高阈值。
- [Codex/ChatGPT Work功能文档](https://learn.chatgpt.com/docs/features)本轮没有找到输入区逐行增高的尺寸规范。

本轮未登录三家竞品App做相同文字和设备的实机对比，不声称三者每个平台、每个版本都使用相同行数。“逐行增长、封顶滚动、可展开”的规格是针对Potato实测问题的设计建议，不是假称测得的竞品像素参数。
